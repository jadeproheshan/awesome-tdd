# TDD 协作

只有一个入口。根据用户想完成的工作选择内部能力，不要求用户记忆步骤名、从头走流程或填写参数表。

## 选择本轮工作

先读当前对话、项目说明、相关代码与测试，复用已确认规则、接口、已审阅测试和完成的步骤。识别本轮范围、所需动作及停止条件；不重复澄清已有结论。仅对影响正确性的未决业务规则提问，常规技术选择可采用合理默认并说明。

用户限定的动作只授权相应工作，不自动启动全流程。用户要求完成多个行为或把功能做完时，采用批量推进。若上下文仍无法确定有实质差异的范围或停点，先问一个最小问题。

| 用户意图示例 | 内部能力与交付 | 默认边界 |
| --- | --- | --- |
| “先帮我理清需求” | 澄清目标、规则、验收与范围，区分已确认、待决和建议 | 不写代码；不强制落盘 |
| “挑下一个最小行为”“列场景” | 根据已有覆盖选择增量，列输入、动作、可观察预期及关键边界 | 不写测试或实现 |
| “只定接口/实体”“搭个骨架” | 复用既有模型，推导最小输入输出、错误语义和必要状态；可补可调用骨架 | 不实现业务；只讨论或只给签名时不改文件 |
| “只写测试”“先看测试” | 按确认行为编写有业务断言的测试，补必要骨架，真实运行，展示代码入口及结果 | 测试审阅后等待，不实现业务 |
| “继续实现”“把这些测试做绿” | 沿用已审阅测试和契约，先运行基线，以足够通用的最小实现满足预期，跑相关回归 | 不扩需求或自动做系统性重构 |
| “重构一下” | 明确范围，建立测试基线，整理命名、重复和职责，保持公开契约及行为，再回归 | 不新增业务功能或改变测试预期 |
| “验收一下” | 按需求运行适用的测试、构建及检查，报告通过、失败、阻塞和未验证项 | 默认只读；明确授权修复后才改代码或测试 |
| “这些行为直接做完” | 按下面的批量流程执行至已授权范围完成 | 默认自动推进；遵循用户指定停点 |

这些是可组合的内部能力，而非安装入口或固定顺序。已有失败测试时可直接实现；缺少实体时从行为推导最小接口，不先搭完整架构。已有功能不得改成占位。实现请求缺少测试时，按用户授权补必要测试；只授权狭窄动作且缺前提时，说明缺口，不擅自扩大任务。

## 批量推进与节奏

默认按依赖顺序逐行为进行：必要契约/骨架 → 测试 → 实际运行 → 实现 → 相关回归；最后整批验收。步骤已完成则复用或跳过。默认不逐步骤反复确认，只做本次实现必要的局部整理，不自动发布、推送或引入新架构。

当次自然语言可改变范围、顺序和停点：

- “全部测试写好跑一下，我看完再实现”：先写整批测试与必要骨架，真实运行并给出可审阅代码，在业务实现前停止；不能只交测试计划。
- “每个行为先看测试”：写完并运行当前行为的测试就停，不实现，也不提前处理后续行为。
- “每步确认”：在首个尚未完成的阶段交付后停住，等待确认再推进；说明本次完成了什么及下一阶段是什么，不因默认 batch 连续执行。
- “继续实现”：沿用此前审阅结果进入实现，不重开需求讨论；之后仍遵守尚有效的范围及确认节奏，除非用户明确修改。
- “只做 A、B”：只处理选定行为；其他需求列为未执行，不默认纳入。
- 用户要求其他顺序时遵循。先实现再补测试可以执行，但如实说明是补测试，不声称走过测试优先的历史。

## 真实性与实现约定

- 预期来自需求及已确认行为。不得为通过而删除/弱化断言、改期待值或硬编码样例；测试与需求冲突时说明依据，按用户决定处理。
- 新测试直接通过时检查其有效性，报告已有实现已覆盖，不破坏正确代码制造 Red。
- 区分业务断言失败、编译/导入错误、环境问题、已有通过和未验证。缺少类型时补最小骨架，使测试能够验证业务；不把编译失败冒充目标行为失败，不把导入通过当业务通过。
- 实际运行可用的测试命令；不能运行时据实交接，不伪造通过。环境修复控制在授权范围，不无界安装或修改无关全局配置。
- 测试验证可观察结果；行为、测试和函数无需一一对应。并发需求应验证业务不变量或原子性，不把无数据竞争等同业务正确；mock 只隔离必要依赖，不替换掉整个被测业务。
- 保持现有项目风格与无关改动，遵循项目的文件位置约定。不强制创建工作台、过程文档、分层架构或额外实体。缺关键覆盖时按授权补最小特征测试，无法确认行为时说明风险。
- 交接简要说明本轮行为、关键改动、真实命令与结果、当前停点及限制。审阅时展示实际测试代码/文件入口；不以长篇计划代替可审阅产物。
