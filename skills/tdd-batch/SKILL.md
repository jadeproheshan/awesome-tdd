# 批量 TDD 实现

## 默认流程

1. 读取已确认需求、用户选定行为、现有代码和测试，识别依赖与最小共用契约。优先复用已有接口；按当前规模组织代码，不预建完整架构。
2. 按依赖顺序逐行为执行：补必要契约和最小骨架 → 写测试 → 真实运行并确认结果 → 实现 → 验证该行为及受影响回归。
3. 相关行为可用表驱动或组合测试，一个实现可覆盖多个场景；不强制 N 个行为等于 N 个测试或 N 个函数。
4. 完成后执行整批回归和适用的构建检查，报告完成行为、命令结果、问题和限制。默认自动推进，不逐行为反复确认；只做本次实现必要的局部整理，不扩大到未授权功能、发布或系统性重构。

## 用户可以调整节奏

用户当次明确指令优先于默认流程。可以整批先写测试、先审阅测试、逐行为确认、跳过讨论、只运行部分阶段或指定其他执行顺序。直接理解自然语言，不要求填写固定参数，不因偏离默认顺序而强行拉回。

- “全部测试写好跑一下，我看完再实现”：先形成整批测试及必要骨架，运行并说明结果，展示测试审阅入口；在业务实现前停止，不将“审阅测试”解释成只审阅计划。
- “每个行为的测试都先给我看”：按行为完成测试与运行后暂停，不推进后续行为或实现。
- “不用等我，直接做完”：按默认逐行为循环自动实现和验证。
- 用户审阅后明确说“继续实现”：复用刚审阅的测试、契约和已确认预期，进入实现，不从头重新询问已确认业务规则。
- “先做其中 A、B”：只处理所选范围；其他项仅列为未执行，不自动纳入任务。

遵循用户停止或修改节奏的后续指令。用户要求先实现再补测试时可以遵循，但据实说明是测试补充流程，不虚构先测试后实现的历史。

## 关键边界

- 实体尚不存在不阻塞 TDD：从行为推导必要类型与接口，使测试能调用，再以业务断言验证。避免编译失败掩盖实际行为验证。
- 新测试已经通过时，检查其有效性并报告现有实现已覆盖；不倒退代码制造 Red。
- 发现影响结果的未决业务规则时，先指出最小决策问题；可独立推进不依赖该决策的已授权行为，但不得越过用户指定的整批审阅停点。
- 环境问题与业务失败分开。不能运行时不得声称测试通过；可在授权范围内修复环境，避免无界安装或改动无关全局配置。
- 并发需求应验证业务原子性或不变量。mock 只隔离必要外部依赖，不把被测业务整体替换掉。
- 避免全程形式化日志；最终用精炼的行为完成清单、实际命令结果及当前停点交接。用户要求测试审阅时给可直接查看的测试代码或文件链接及关键断言。

## 执行约定

- 优先遵循用户本次指定的范围、节奏和停点；本技能的默认流程是可调整的起点，不是强制用户遵循的仪式。不把“我指定了一个步骤”解释成授权运行全部步骤。
- 先读项目说明、现有需求、相关代码和测试，复用已有契约。业务规则存在影响正确性的歧义时再询问；不要猜测关键规则，也不要重复确认已经明确的事项。
- 仅修改授权范围内的文件，保护现有改动。遵循项目的生成文件位置规则。只有用户要求保存过程记录时才新增记录文件，不强制创建工作台或新架构。
- 测试预期来自需求或已确认行为。实现阶段不通过弱化断言、删除覆盖或硬编码样例来过关；发现原测试与需求冲突时说明依据，再按用户指令处理。
- 使用项目真实可用的测试命令。区分行为失败、编译失败、环境阻塞与已有通过；不伪造执行结果，不为制造 Red 故意破坏正确实现。无法运行时明确未验证的范围。
- 输出以本轮行为、关键改动、实际验证和当前停点为主，简洁即可；未执行的后续步骤只列为可选下一步。
